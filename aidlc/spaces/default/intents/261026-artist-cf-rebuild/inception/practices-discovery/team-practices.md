# Team Practices

> Affirmed by the owner in the practices-discovery interview
> (`practices-discovery-questions.md`, Q1 to Q8, summary confirmed "Looks
> correct"). This is a solo, greenfield, local-only project in the `mvp` scope.
> What was inspected and why each choice was made is in `evidence.md`.

## Way of Working

- We work solo: one person builds, reviews and approves. There is no second
  reviewer, so the approval gates and the pre-merge check are our review.
- We use **trunk-based development** with **`main`** as the trunk. The
  repository's `master` branch is renamed to `main` before the first commit, and
  `main` is both the base branch and the merge target for every Construction
  Bolt.
- Each Construction Bolt gets its own short-lived branch and worktree, and is
  **squash-merged** into `main` as one commit named by the Bolt slug.
- Commits we ask for outside Construction go on the branch we are on; no extra
  branches unless we ask for one.
- Commit messages are short, imperative sentences ("Add FAISS index builder").
- The code stays **local for now**: no remote and no pull-request flow in v1. A
  private GitHub repository may be added later; when it is, the GitHub Actions
  workflow described under Testing Posture is switched on.

## Walking Skeleton

- **Yes: we build a thin end-to-end slice first**, before the real features go
  in.
- The first Unit is the smallest slice that runs the whole way through: read a
  small sample of the ListenBrainz dump in place, train a tiny ALS model with
  Spark, build a FAISS index, and answer one similar-artist lookup through the
  FastAPI app. Genres, name-search quality, the web screens and the full-size
  data come after.
- The skeleton is verified by a Construction Verification Command that the owner
  chooses and authorizes during Construction, which must show the real
  end-to-end result, followed by the owner's skeleton checkpoint approval.

## Testing Posture

- **Methodology**: custom
- **Methodology evidence**: The owner chose a mix of cadences in the interview
  (Q3: "test-first (TDD) for search, lookup and the web layer; test-after for the
  data pipeline and model training"). The search, lookup and web layers are pure
  Python with clear inputs and outputs, so tests can lead; the Spark data
  pipeline and the model training are exploratory and data-shaped, so tests
  follow the implementation. The existing app has no tests, so there was no
  prior habit to keep.
- **Ordering**: For search, lookup and the web layer we write the tests before the implementation; for the data pipeline and model training we implement first, then write and run that layer's tests before moving on.
- **Coverage floor**: 80% line coverage, measured with `pytest-cov`. The floor
  is never lowered to make a step pass.
- **Tooling**: `pytest` and `pytest-cov` in the `uv` dev dependency group, run
  with `uv run pytest`.
- **Test data**: tests never read the full dumps. Spark and FAISS steps are
  tested on small fixture files under `tests/fixtures/` (a few hundred synthetic
  listen rows), with one local `SparkSession` shared across the test session to
  keep runs fast.
- **Test types** (Test Strategy: Standard): unit tests for pure logic,
  integration tests for each pipeline step on fixture data, and API tests for the
  FastAPI endpoints with `TestClient`. The lookup-speed check against the 200 ms
  target (constraint TC-4) runs separately from the default suite because it
  needs the full-size index.
- **Pre-merge check**: one local check command runs before every Bolt merge and
  must pass: `ruff check`, `ruff format --check`, `ty` on our own code, and
  `pytest` with the coverage floor.
- **GitHub Actions**: a workflow running the same check is set up in the
  repository but stays switched off until the code is pushed to GitHub; once it
  is, it runs on every push alongside the local command.

## Deployment

- **No deployment in v1.** The app runs locally only (constraint TC-5); public
  hosting, cloud deployment and deployment preparation are out of scope, and the
  Operation phase is skipped for this intent.
- **"Released" in v1 means**: the Bolt is squash-merged into `main`, the
  pre-merge check passes, and the app starts locally (`uv run uvicorn ...`)
  against the current model files.
- We tag **`v0.1.0`** on `main` when the core scope is done.
- Rolling back means reverting the Bolt's squash commit on `main`. Built data
  and model files are regenerated by re-running the pipeline steps in their
  documented order; they are never committed.
- The framework default (deploy on merge to staging, manual approval for
  production) does not apply yet. We keep it as the stance for a later intent
  that adds hosting.

## Code Style

- **Python 3.12**, managed with **`uv`**; the project is a `src/` layout package
  built with `uv_build`.
- **Formatter**: `ruff format`, line length 100.
- **Linter**: `ruff check` with the rule sets `E`, `F`, `W`, `I`, `B`, `UP`,
  `SIM`, configured in `pyproject.toml` (the same settings as the existing app).
- **Type checker**: `ty`, at a pinned version in the dev dependency group,
  checking our own code. Modules and call sites that depend on PySpark, FAISS
  and UMAP are excused where those libraries' typing gets in the way (through
  `ty` configuration or targeted ignores, never by turning the checker off).
- Lint, format and type checks are part of the pre-merge check; a failure blocks
  the merge.
- `pytest`, `pytest-cov` and `ty` are deliberate additions to the existing app's
  toolset, chosen by the owner in the interview (Q3, Q6); they are development
  tools and do not change the fixed runtime stack (Python, Spark, FAISS, FastAPI,
  UMAP).
- Naming is Python-idiomatic: `snake_case` for modules, functions and variables,
  `PascalCase` for classes.
- Agents read the `ruff` and `ty` configuration first and suggest style changes
  only where those tools do not already cover them.
